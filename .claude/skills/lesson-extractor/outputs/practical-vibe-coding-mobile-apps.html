Field primer

This video is about building a phone app with the help of AI coding assistants. A few words on the field so the rest lands.

Mobile app development is writing the software that runs on phones. React Native is a popular framework that lets you write one codebase (in JavaScript / TypeScript) that runs on both iPhone and Android, and Expo is a toolkit that makes React Native much easier to start, run, and ship. AI coding assistants (like Claude Code, Cursor, GitHub Copilot, or OpenAI Codex) are tools where you describe what you want in plain English and the AI writes and edits the code in your project for you.

The term in the title, vibe coding, was coined in early 2025 to mean leaning fully on AI and barely reading the code. It is fast but tends to collapse on anything serious. This tutorial pitches a disciplined middle path it calls practical vibe coding: keep AI's speed, but add just enough structure (a project rules file, scoped prompts, constant verification) that the AI always knows what it is working on and you never lose the thread. The app being built (a Duolingo clone with lessons and a talking AI language teacher) is just a realistic vehicle for showing the workflow on something bigger than a toy.

Before you dive in

Prerequisites

Genuinely essential

  • Basic comfort with a code editor and a terminal (you will run commands and edit files, even if AI writes most of the code).
  • Node.js and npm installed (so npx works).
  • An AI coding assistant subscription. The video uses Claude Code on the Sonnet model (about $20/mo) but says any agent works.
  • A phone with the free Expo Go app, for the early part of the build.
  • Free accounts for the services used: Clerk, Stream, PostHog, plus GitHub and CodeRabbit.

Helpful, not required

  • Prior React or React Native knowledge. The creator recommends his "React Native full course 2026" first if you want to understand the framework by hand.
  • Understanding of authentication, state, and APIs (it helps you write better constraints, but the AI fills gaps).
  • Needed only for the later half: a native build environment. macOS + Xcode for iOS, or Windows/Linux + Android Studio. This is required only once you add Stream's audio (a native module) and is not needed for the first ~12 features that run in Expo Go.
  • No Python knowledge needed despite the app including a Python service: the point is that AI writes it for you.
Vocabulary

Glossary

Plain-English meanings for the terms the video assumes. (Spellings that are garbled in the transcript are given correctly here.)

AGENTS.md
A markdown file at the root of the project that tells AI agents how the project works: role, stack, folder structure, styling rules, patterns. The first file the agent reads. The backbone of this whole method.
Agent / coding agent
An AI assistant that can read and edit your codebase (for example Claude Code, Cursor, Copilot, OpenAI Codex, Windsurf).
Agent skills
An open-source standard: a reusable instruction pack that teaches your AI how to use a specific tool correctly (and on its current version). Installed with npx skills add.
MCP
Model Context Protocol. Lets AI tools query a service directly (for example asking PostHog "which screen has the highest drop-off?") and act on the answer.
Context7
A service that fetches the latest documentation for a library so the AI does not rely on outdated training data.
React Native
Framework for building iOS and Android apps from one JavaScript / TypeScript codebase.
Expo
A toolkit on top of React Native that simplifies setup, running, and shipping.
Expo Go
A free app you install on your phone to preview your project instantly by scanning a QR code. No full build needed. Works only until you add native modules.
Development build
A custom build of your app compiled with native code included (needed once you use native modules like Stream's audio). Same Expo experience, but built through Xcode or Android Studio.
Expo Router
File-based navigation for Expo. Folders and files become screens and routes.
Route group
A folder in parentheses like (auth) that organizes screens without adding to the URL path. Purely for structure.
Metro bundler
The tool that compiles and serves your React Native code during development.
pre-build
An Expo command that turns your config into a full native ios/android folder. The --clean flag wipes old generated code first.
NativeWind
A library that lets you write Tailwind CSS utility classes (like flex-1, text-center) to style React Native apps. The video uses v5.
Tailwind CSS
A styling system based on small utility classes instead of separate stylesheets.
Zustand
A small state-management library: a shared place to keep app state many components need, without prop-drilling or Redux boilerplate. (Transcript garbles it as "Zastand / Zustin".)
AsyncStorage
Local key-value storage on the device for small, non-sensitive data (settings, flags, cached state). Used here instead of a database for the MVP.
Clerk
A managed authentication and user-management service: email/password, social login, OTP, sessions, billing.
OAuth / SSO
"Sign in with Google / Apple / Facebook." Single sign-on through an external provider rather than a new password.
OTP
One-time passcode: the short numeric code emailed for verification or passwordless sign-in.
JWT / JWKS
A signed token proving who a user is (JWT), verified against the provider's public keys (JWKS). Used in the security fix so the server trusts the authenticated caller, not a user ID from the URL.
Token provider
A small server endpoint that mints a secure token for a service (here, Stream) so the secret key never ships in the app. Built with Expo API routes.
Expo API routes
Server-side endpoints inside an Expo app (similar to Next.js API routes). Used to keep secrets off the client.
Stream
A service handling real-time audio/video infrastructure: sessions, participant state, low-latency transport, connection lifecycle.
Vision Agents
Stream's open-source Python framework for real-time voice/video AI agents. Here it runs as a separate service that joins the call as the AI teacher.
WebRTC
The browser/device technology for real-time audio and video. The audio transport under the hood.
VAD
Voice Activity Detection: deciding when someone is speaking. "Server VAD" (energy-based) fires fast; "semantic VAD" waits to understand intent and is slower.
OpenAI Realtime
OpenAI's low-latency speech model. The brain of the AI teacher's spoken conversation.
PostHog
A product-analytics platform: event tracking, funnels, retention, session replays, feature flags, with an AI wizard that auto-instruments your project.
CodeRabbit
An AI code-review tool that reviews each pull request (and works in the editor), flagging bugs, security issues, and style inconsistencies.
Homebrew / CocoaPods
macOS tooling: Homebrew is a package manager; CocoaPods links native iOS libraries into an Xcode project (pod install).
XP
"Experience points." The gamification reward shown per lesson, Duolingo-style.
The big picture

Takeaways

The workflow is the product

The app is disposable; the repeatable AI-development method is the thing to carry to your next project. "The product will change, the workflow doesn't."

Two failure modes, one middle path

Pure vibe coding gives speed without direction; over-planning gives docs without an app. Practical vibe coding keeps the speed and adds just enough structure.

Think behavior, not code

You no longer write the lines. You decide architecture and describe how features should behave. Planning and clear specs matter more than syntax now.

One task per prompt, verify each

Scope every prompt to a single feature and test it before moving on. When something breaks, the cause is contained because you changed only one thing.

Context beats clever prompts

Most prompts in the build were small. What carried quality was reusable context (AGENTS.md), feature isolation, and consistency, not prompt wizardry.

Reviewing AI code matters more

Because you did not write it, review is more important, not less. An automated reviewer caught a real auth security hole and a committed secrets file.

Ship MVP on hard-coded data first

Build the full UI and features on typed, hard-coded data, then add a database later. Optimizes for iteration speed and getting to market.

Know when to stop following

The most underrated skill: stop copying tutorial steps and start experimenting once you understand the moving pieces. The video deliberately hands one feature to you.

The core, part 1

The method: practical vibe coding

The crash-course principles, as numbered rules. These are the reusable part.

1

Avoid both extremes

Pure vibe coding (give in to AI, never read the code) flies for three features then collapses: you ask for one fix, something else breaks, and you are staring at code you cannot explain. Over-engineering is the opposite trap: days of folder structures, tokens, and architecture docs before a single screen exists, which feels productive but ships nothing.

The fix is a disciplined middle: AI speed plus just enough structure, building one feature at a time and verifying each before the next.

2

Put project context in one file: AGENTS.md

Create AGENTS.md at the project root. It is written for the AI, not for you, and is the first file tools like Cursor, Claude Code, and Windsurf read. Without it you re-type the same context every prompt, and the moment you forget a line the AI invents its own choice (a different state library, folder convention, or styling approach), so across 20 prompts the codebase looks like five people built it.

It contains: a role ("you are an expert React Native + Expo engineer, prioritize clarity over abstraction"), a one-paragraph overview, the stack (one line per library so AI stops suggesting alternatives mid-build), the folder structure, styling rules and quirks, and the patterns to follow. Do not write it perfectly up front; add a rule when a problem keeps recurring.

"Solve it once, document it, move on." A recurring NativeWind + SafeAreaView issue became one rule and the AI never repeated the mistake.

3

Every prompt has the same four parts, in order

1) Point to AGENTS.md: "Read AGENTS.md first and follow it strictly," every time, because agents do not remember previous sessions. 2) One task: exactly one feature, screen, or integration (not "set up NativeWind and build onboarding and add auth", which is three prompts hiding as one). 3) Constraints that protect what works: tell it what not to break ("do not change the screen design", "keep the existing Stream audio flow intact", "don't expose secrets"). 4) Design references: attach an image when the task is visual; AI reads a layout better than a description of one.

"A perfect prompt is just an instruction with a defined scope": what you are building, what you are not touching, and what rules it already knows from the file.

4

Constraints are about behavior, not code

The common mistake is writing a constraint that does not constrain anything, because people think about code when they should think about behavior. Do not tell the AI how to write the code; tell it how the feature should behave: what already works and must stay, what may change, what is off limits. Examples: "if anything is unclear, ask before implementing"; "do not expose any secrets"; "keep the existing Stream audio flow intact."

Find constraints by looking at the app like a product engineer: what could go wrong for a user, what might the AI accidentally refactor that already works.

5

For non-visual features, describe behavior and add a test utility

State management, auth logic, and backend integrations have nothing to attach. Describe the behavior instead ("store the selected language in Zustand with AsyncStorage; if an authenticated user has no language, route them to selection, then home; preserve the existing UI"). Also prompt for the infrastructure that lets you verify it, like a temporary "clear storage" button you remove later.

Prompt for the thing that lets you test the feature, not just the feature itself.

6

Keep the AI on the current version of your tools

AI training data lags by months, so it writes code using deprecated methods or old APIs that break at build time. Three fixes: paste the current docs into the prompt under a divider; install agent skills once so the AI always uses the right version (Expo, Clerk, Stream all publish them); or use Context7 / MCP to pull the latest docs on demand.

When unsure whether the AI knows a library's current version, assume it does not, and feed it the real docs.

7

When something breaks, write one targeted fix

Breakage is normal, not a failure of the method. Do not re-explain the feature or paste the codebase. State the problem, state the correct behavior, and add a constraint if needed: "the verification modal appears behind the keyboard on iOS; it should sit above it; don't change any other modal behavior or layout."

One problem, one fix, one verification. Often the simplest move is pasting the raw error message straight into the chat.

8

Practice session hygiene

When you finish a feature, close the chat and start a fresh session. Stale context from earlier work leaks in, confuses the agent, and spends more tokens. Stay in the same chat only when the next step is directly tied to what you just built (for example fixing an error from the same change).

Fresh session per feature; same session only for tightly-coupled follow-ups.

9

The tooling is your call; spend tokens wisely

The workflow is agent-agnostic (Copilot, Claude Code, Codex, Cursor, Windsurf all work the same once you are inside). The video uses Claude Code on Sonnet with thinking on (Claude Pro ~$20/mo), optionally topped up with OpenAI Codex Go (~$8/mo). Tip shown: you can speak prompts with the mic button instead of typing.

Pick the tool you already pay for; the thinking and the specs are what matter.

10

Review everything, and build on hard-coded data first

Run a code review on every change (the video uses CodeRabbit on each PR and in the editor); reviewing AI-generated code matters more than reviewing hand-written code. Separately, build the full UI and MVP on typed hard-coded data before adding any database, so you can iterate fast and reach market, then swap in a backend once the structure is proven.

"That's how good developers build: MVP the features with hard-coded data first, integrate the database after."

11

Eventually, stop following and start experimenting

Near the end the creator deliberately hands one feature (live captions) to the viewer to attempt first. Once you understand the moving pieces, the real skill is guiding the AI yourself using the context it already has, not memorizing prompts.

"Knowing when to stop following tutorials step by step and start experimenting on your own" is called the most underrated skill in AI-assisted building.

Fact check

Context and corrections

This is a hands-on technical tutorial, so most of it is just demonstrated and self-verifying. The checkable claims are mostly the sponsor pitches; they hold up as of mid-2026, with one timing nuance.

Supported

"Andrej Karpathy, one of OpenAI's founding members, posted about vibe coding." Correct. Karpathy (an OpenAI co-founder) coined "vibe coding" in a February 2025 post; the term was even Collins Dictionary's 2025 Word of the Year. (The transcript's "Andre Carpathy" is just a spelling slip.)

Supported

"Clerk's free plan gives up to 50,000 monthly retained users." Accurate for when this video is set. Clerk raised its free tier from 10,000 to 50,000 monthly active users in February 2026. Worth knowing the nuance: if you are following along from materials made in 2025, the number was 10,000 then, so verify the current limit on Clerk's pricing page rather than trusting any video.

Supported

"Stream's Vision Agents is open-source." True. It is an open-source Python framework for real-time voice/video AI agents (on GitHub at GetStream/Vision-Agents), with day-one support for models like OpenAI Realtime and Gemini Live. You do use a paid OpenAI key for the model and Stream's network for transport, but the agent framework itself is genuinely open.

Supported, with context

"Nvidia's CEO said they use CodeRabbit all over Nvidia." Jensen Huang is on record saying "We're using CodeRabbit all over NVIDIA," so the quote is real. The implied argument ("good for a huge company, so good for your project") is a marketing appeal-to-authority, not evidence that it is right for your use case. Useful tool, but judge it on your own results.

Opinion

"This is the only way to build mobile applications with AI without getting lost in spaghetti code." Presented as fact, but it is a stylized pitch. The underlying principles (project context file, scoped prompts, verify-as-you-go, review everything) are widely endorsed, yet they are not the single "only" path, and they sit inside a sponsored stack. Take the workflow; stay skeptical of "only."

Opinion

"You don't need to learn Python; just understand the logic." / "It's not the lines of code that matter." A reasonable stance for shipping an MVP, and broadly true that AI lowers the syntax barrier. But it is a judgment call, not a settled fact: for debugging, security, and long-term maintenance, understanding the code you ship still matters, which is partly why the video itself leans so hard on automated review.
